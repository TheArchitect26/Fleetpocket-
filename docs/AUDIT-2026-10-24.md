## Findings to fix before a live pilot

**R01 — P1 — Historical POD/closure can empty the vehicle's newer load.**

Evidence: [synchronize_load, migration 006:55–61](../supabase/migrations/006_operational_integrity.sql#L55) sets a vehicle to Empty for `Delivered`, `POD Received` and `Closed`, without checking which job currently owns its load. The active-assignment index at lines 27–28 excludes Delivered/POD Received jobs. The [domain helper](../lib/domain.ts#L17) repeats this rule.

Normal failure sequence:

1. Job A is Delivered, so its vehicle becomes Empty and can take another job.
2. Job B loads that vehicle, correctly making it Loaded.
3. A's paperwork arrives later; A advances to POD Received or Closed.
4. The trigger changes the shared vehicle to Empty although B is still Loaded/In Transit.

The current helper reproduced the Loaded → Empty corruption locally. A SQL witness is supplied for the actual trigger/RPC path. Existing tests close a single job before another begins and miss this case.

Fix: distinguish physical loading/unloading from paperwork completion. Only the current cargo/assignment owner may change physical load state; POD Received/Closed should not blindly unload the vehicle. Prefer deriving load state from current consignments or explicit physical events.

Acceptance: finish A's paperwork after B loads, including delayed/repeated requests. B and its WhatsApp update must stay Loaded. Test two jobs on one vehicle, not only one complete journey.

**R02 — P1 — A same-status dispatch request can erase an ETA and leave it pending permanently.**

Evidence: [dispatch_job](../supabase/migrations/006_operational_integrity.sql#L76) accepts `next_status` equal to the current status. The trigger's transition/version guard runs only when the status differs. However, `AFTER UPDATE OF status` still invokes [queue_after_dispatch](../supabase/migrations/007_durable_eta.sql#L49) when the column is assigned its existing value. [enqueue_job_eta](../supabase/migrations/007_durable_eta.sql#L45) uses `ON CONFLICT DO NOTHING` and then clears the current ETA regardless of whether work was inserted.

Source-derived reproduction: complete a work item for an In Transit job, then call the valid dispatch endpoint/RPC with current version and `status: In Transit`. The operational version remains unchanged; the old completed work conflicts with the unique key; the job becomes pending with no ETA; no new pending work exists. A fresh GPS/route change is needed to recover. The frontend helper rejects the same-state transition, but the server RPC does not use that helper. This is an exposed API-contract problem even though the normal next-stage button advances correctly.

Fix: reject an unsupported no-op or make it truly idempotent without side effects. Fire queue invalidation only for actual changes, and do not clear a valid estimate when an existing completed work item is reused. Define duplicate/retry semantics for commands explicitly.

Acceptance: repeat current-status commands before/after ETA completion, with valid and stale versions. The result must preserve ETA/work state or return a controlled conflict. Execute the supplied SQL witness and convert it into a regression test.

**R03 — P1 — Default worker throughput can fall behind ordinary GPS rates and process obsolete work first.**

Evidence: [worker POST](../app/api/worker/route.ts#L11) claims exactly five items per invocation. The [deployment cadence](REMEDIATION.md#L36) recommends one invocation per minute. Each new promoted GPS event creates work for the active job; [claim_eta_work](../supabase/migrations/007_durable_eta.sql#L65) takes oldest eligible work and checks source supersession only during completion, after making the routing request.

Analytical example, not a benchmark: 12 active vehicles sending one update per minute create 12 work items/minute. One documented worker call processes at most five/minute, so backlog grows by at least seven/minute before retries and dispatch-generated work. Older work is likely superseded by newer GPS but still consumes routing capacity. Even one vehicle updating every ten seconds can exceed that default service rate.

Fix: keep every GPS event in history, but coalesce/debounce ETA work by current job/source; cheaply discard obsolete work before external routing. Configure sufficient draining/concurrency, tenant fairness and provider limits. Measure arrival rate, oldest work age, completion/supersession ratio and queue lag. Do not infer capacity from a passing two-event SQL test.

Acceptance: sustain representative fleet sizes and provider cadences, including outages/recovery, without unbounded lag. Demonstrate an ETA freshness target, fair customer service and a bounded route-call budget.

**R04 — P1 policy gate — Every GPS event requires a new human ETA approval.**

Evidence: [enqueue_job_eta](../supabase/migrations/007_durable_eta.sql#L46) clears approval/current ETA on each new source; completion creates an unapproved version, and [approved_etas](../supabase/migrations/007_durable_eta.sql#L114) requires it to match the vehicle's latest GPS event. [The runbook](REMEDIATION.md#L34) explicitly documents this strict policy.

This is an intentional policy rather than an undisclosed implementation bug. It nevertheless needs operational acceptance: 12 vehicles at one event/minute can require up to 720 approvals/hour to keep every new version visible. A new GPS event withdraws the prior approval, leaving customers without an ETA until processing and review finish. Faster providers make the usable publication window smaller.

Fix: agree a publication policy with MCY. Options include a visibly timestamped still-valid last-approved estimate while a new calculation is pending, or human-approved rules/tolerances that escalate significant changes. Preserve immutable version/provenance evidence and honest freshness labels; do not silently call an unreviewed estimate approved.

Acceptance: run an actual controller shift simulation with expected provider rates. Quantify approval workload and the proportion of customer time with an approved valid ETA. MCY must accept those operating targets before rollout.

**R05 — P1 — Loading-stop ETA is still treated as delivery ETA in key views and metrics.**

Evidence: ETA work now correctly distinguishes loading and delivery stops. The drawer and WhatsApp text show that distinction, but the [fleet table](../components/control-tower.tsx#L40) and dispatch cards display an undifferentiated ETA. [Delay counts](../components/control-tower.tsx#L28) and [performance reports](../components/control-tower.tsx#L54) compare that timestamp to the job's final `scheduled_at` regardless of `eta_stop`.

Example: arrival at loading is estimated for 10:00; final delivery is due at 14:00, but the remaining trip plus loading would finish at 18:00. The current comparison can count the journey as within window using 10:00 versus 14:00. The application has no final forecast including that remaining work.

Fix: expose distinct next-stop and final-delivery estimate types in every view/export. Compare each estimate only with its corresponding stop window. Do not mark final delivery on time when final ETA is unknown. Add remaining-route/service-time forecasting as a separate feature.

Acceptance: before-loading and in-transit examples show the right estimate labels and delay metrics. Unknown final ETA must remain Unknown rather than count as on time.

## Reliability and completion findings

**R06 — P2 — Atomic writes are read back as a non-atomic composite workspace.**

[workspace GET](../app/api/workspace/route.ts#L8) performs separate queries for vehicles, jobs, documents and ETA metadata. A dispatch transaction between those reads can return the vehicle before loading and the job after loading, despite the database writer being atomic. Separate ETA merging can also combine a job/route snapshot with a newer estimate. This is source-derived, not a database race exercised here.

Use one authorised snapshot RPC/statement or versioned records that the client reconciles before presenting a coherent trip. Test a deliberate mutation between workspace subqueries and verify no contradictory operational message can be generated.

**R07 — P2 — A successful write can be presented as a failed command when refresh fails.**

The [client API helper](../components/control-tower.tsx#L31) awaits `refresh(true)` before returning its already-successful mutation result. If refresh fails, creation/approval callers enter their error path and may leave the form open. A user retry can repeat a non-idempotent creation. There is no idempotency key on create-job requests.

The actual extracted helper reproduced this boundary locally with a successful write response and a rejected refresh: it threw, and retry issued a second write. This was a stubbed network probe, not two real job insertions.

Separate command success from refresh status. Keep the committed entity/result, show “saved; refresh pending”, and use idempotency keys for non-idempotent creation. Test successful commit followed by 503, timeout and session-refresh failure.

**R08 — P2 — The record cap still affects operations and reports.**

The truncation banner is an improvement, but [workspace reads](../app/api/workspace/route.ts#L9) still stop at 1,000 rows/table. Vehicles/jobs have no stable ordering or pagination; aggregate counts, job selection and CSV exports still use the subset. A sufficiently old dataset can omit a live job, not merely old history. Add paginated tenant-scoped reads and server-side counts/current assignments, and verify >1,000 records with live work outside the initial page.

**R09 — P2 — Every poll rebuilds the map and resets the controller's viewport.**

The refresh hook replaces workspace arrays. [FleetMap](../components/fleet-map.tsx#L6) depends on those vehicle/tenant arrays, removes the map on cleanup and constructs a new centered/zoomed map on each effect. With polling, a controller's pan/zoom can reset every 15 seconds. The error flag also lacks a successful-load reset.

Create the map once, update sources/markers separately and preserve viewport/selection. Test a zoomed map through two refresh cycles and transient tile recovery. This regression is exposed by the new live-refresh behavior; the original static demo did not exercise it.

**R10 — P2 — HTTP failure semantics are still inconsistent across endpoints.**

The new typed helper and dispatch errors are useful, but [members GET/POST](../app/api/members/route.ts#L4) still throw plain `Error('Forbidden')`, which [failure()](../lib/server.ts#L35) maps to 500. Several invalid-upload conditions also become 500. Document GET maps both absent metadata and query errors to 404. Legacy alert acknowledgement can return success when no row matched.

Finish the typed-error migration, separate missing rows from database outages, and test expected status codes for every role/endpoint. Do not rely on tests accepting any status >=400 for security or availability checks.

**R11 — P2 — WhatsApp approval and scheduling remain incomplete.**

The [update endpoint](../app/api/updates/route.ts#L4) inserts and approves in two transactions. Existing table update permissions still allow a controller to modify an approved message without clearing approval. Interval metadata is not a durable reminder schedule; the UI retains “Approved update” after its interval becomes overdue. Latest-first ordering is now improved, but it does not implement due processing.

Add immutable message versions, transactionally recorded approver/time/source facts, due tasks and accurate overdue state. Keep manual final sending and avoid claiming message delivery merely because WhatsApp opened.

**R12 — P2 — Queue and incident failures do not have adequate operational handling.**

The worker reports `retry_or_failed` for both retryable and exhausted work. It can return 200 when every route calculation failed but failure persistence succeeded. There is no authorised dead-letter review/requeue UI, queue-lag alert or deployed scheduler/monitor. Existing `monitor_fleet` logic still lacks automatic condition recovery and can recreate acknowledged conditions; document expiries dedupe by vehicle/title and omit driver-record dates.

Add business-level worker health, classified failure causes, pending/failed counts, lag/age metrics, audited retry/recovery and a condition-based incident lifecycle. A 200 receipt/processing response is not sufficient evidence that fleets are receiving ETAs.

**R13 — P2 — Combined customer actions still default to an implicit first tenant.**

Per-tenant capability data now exists, but combined-scope handover notes, summaries and team administration still choose the first tenant. Mixed controller/viewer memberships can produce hidden legitimate controls or visible actions that later fail authorisation. Backend checks are stronger than the UI model.

Require explicit tenant selection for tenant-owned writes, label summary scope, clear derived summaries on scope change and compute per-row capabilities. Test a user who controls A and only views B.

**R14 — P2 — File handling and production operating controls are unfinished.**

Upload ownership and release are now much stronger. They do not implement malware scanning, quarantine, orphan cleanup, quotas or consistently enforced ingress size limits. Native provider authentication/connection registry, hosted scheduler, monitoring, backup/file restore, retention, restore drills and load/security testing remain unprovisioned. Credential binding to one configured tenant/provider is an integration boundary, not full Cartrack/Netstar/MiX support.

These are acknowledged release requirements, not features verified by the local authenticated tests. Provision and prove them in staging before a real fleet depends on the application.

**R15 — P2 — The expanded suites still miss the newly identified operating scenarios.**

The four authenticated workflows are meaningful progress: real cookies, object bytes, role denials and a full single-job journey are exercised. The suite still does not cover overlapping historical/current jobs on one vehicle, same-state RPCs, sustained provider cadence, loading-versus-delivery metrics, mutation-success/refresh-failure, stable map viewport, a real HTTP worker/provider adapter, fairness, or customer publication workload. Several pgTAP fixtures seed states directly, which cannot replace full multi-job command sequences.

Add targeted regressions for R01/R02/R05/R07, then realistic provider/failure/load simulations for R03/R04/R12. Preserve current tests rather than treating a larger test count as proof of operating capacity.

**R16 — P2/P3 — Product completion and maintainability remain substantial work.**

Fleet editing/reassignment/archive/import, managed groups, invitations/MFA/recovery, historical SLA reporting, structured shift ownership, mobile bearer-token APIs, accessible dialog focus handling and URL-backed navigation are incomplete. Schema/domain nullability and constraints still diverge. The controller component remains large and compressed; only a limited set of reusable UI primitives exists. Audit snapshots are useful, but deletion history and immutable WhatsApp evidence are incomplete.

Keep these explicitly scoped in the backlog. Complete the P1 invariants first; then build daily controller workflows and production operations rather than presenting all six product phases as finished.

## Recommended next implementation batch

1. **Write the multi-job and no-op regression tests first.** Use delayed POD for A after B loads, and a completed ETA followed by a same-state RPC. Expected behavior should fail against the current code.
2. **Fix physical load ownership and dispatch idempotency.** Keep paperwork from mutating another trip's load, and keep no-op/replayed commands from invalidating completed work.
3. **Make ETA processing and publication viable at provider cadence.** Coalesce obsolete work, drain at measured capacity with tenant fairness, add queue-health/recovery controls, and agree the customer publication policy with MCY. Test typical 10-second/60-second feeds and outages.
4. **Separate loading ETA from delivery forecast everywhere.** Correct labels, windows, exports and performance metrics; show unknown final arrival honestly.
5. **Repair read/mutation consistency and map updates.** Use a coherent snapshot/version contract, distinguish commit success from refresh failure, add creation idempotency, and preserve map viewport while data changes.
6. **Then complete the remaining daily-workflow and deployment gates.** Pagination, alerts/reminders, fleet management, scanner/recovery controls, native provider integration, hosting, backup/restore and independent security/accessibility/load acceptance remain necessary.

**Immediate recommendation:** fix R01 and R02 before adding more features or connecting a live fleet. They are deterministic correctness problems in normal lifecycle/API behavior. Address R03/R04 alongside any live tracking pilot, because the default documented operating cadence cannot support normal multi-vehicle telemetry reliably.
