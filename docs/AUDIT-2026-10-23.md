# Fleet Pocket audit — 23 October 2026

**Decision: suitable for continued development and a restricted fictional-data demonstration. Not ready to operate a live customer fleet.** Passing CI establishes a useful implementation baseline, but important operational invariants and integration paths remain incomplete.

This audit reviews the application against the original MCY requirements. It makes no application changes. Findings below are source-supported unless explicitly marked as locally reproduced or externally verified. Recommendations are proposed work, not fixes already applied.

The application job includes ESLint, TypeScript, unit tests, a production build, Chromium workflows and the production dependency audit.

**Severity**

- P1: fix before a live fleet pilot, or explicitly restrict the pilot so the affected feature cannot be relied on.
- P2: required for a dependable production release; resolve in the indicated sequence.
- P3: maintainability/delivery improvements after the essential invariants are secured.
- No confirmed anonymous cross-tenant data disclosure was established by this review. That statement is limited by the test coverage described below.

## What is already useful

The rebuild uses Next.js/TypeScript, Supabase and MapLibre without importing an earlier architecture. Tenant-owned rows consistently carry `tenant_id`; composite foreign keys prevent many cross-tenant links. Access depends on explicit memberships rather than an automatic staff-wide tenant grant. Raw ETAs are withheld from the normal customer job view, and unpublished ETA history is controller-only. Worker credentials stay in server modules. Documents use a private bucket and short-lived signed URLs. GPS ingestion locks the vehicle row, records event IDs and does not replace a newer confirmed position with an older event. Demo GPS is labelled simulated. The MCY message structure includes both trailer lines and supports trailerless vehicles. The UI has useful fleet filters, profiles, dispatch cards, reports and handover notes.

Those foundations should be retained. The main work now is to enforce business invariants, exercise authenticated production paths, and establish dependable update/recovery mechanisms.

## Priority findings

**F01 — P1: The controller workspace is a snapshot, not a live tracking workspace.**

Evidence: [control-tower.tsx:19](../components/control-tower.tsx#L19) fetches `/api/workspace` only on initialization. The interval updates the local clock. Other refreshes follow the current user's mutations; there is no polling or Realtime subscription.

Impact: another controller's dispatch action, a new GPS reading, ETA, document or alert can remain invisible until reload. A clock-based stale indicator can even age an old local reading while fresh GPS already exists in the database.

Recommendation: add authenticated, tenant-scoped refresh or Realtime invalidation, server timestamps, a last-successful-sync indicator, reconnect/backoff behavior and an explicit stale-workspace warning. Preserve filters and selection during refresh.

Acceptance: with two sessions open, a database GPS/status update becomes visible without reload within a defined latency target. Disconnecting the data connection visibly marks the workspace stale, and reconnect restores consistency.

**F02 — P1: GPS ingestion and ETA processing are not durably connected.**

Evidence: [tracking/route.ts:6](../app/api/tracking/route.ts#L6) commits `ingest_gps`, then performs routing inline. A duplicate/old event returns immediately. Routing failures return `null`; a job-query error is ignored through `jobs.data || []`.

Failure scenario: GPS is committed; the process crashes or routing/persistence fails. Retrying the identical event reaches the duplicate branch and never retries its ETA. A successful HTTP response can also mean GPS persisted while no ETA was produced. Multiple applicable jobs can make the HTTP call exceed practical request budgets.

Recommendation: atomically persist the GPS event and a durable work item. A separate worker should calculate ETA with idempotency, bounded retries, backoff, observable failure status and a dead-letter/recovery mechanism. Check query errors explicitly. Distinguish event receipt from completed enrichment.

Acceptance: terminate processing after GPS commit and prove the ETA eventually completes once, using the same event, without requiring a new GPS signal. Exercise provider timeout, job-query failure, persistence failure and worker restart.

**F03 — P1: ETA calculation and customer approval are vulnerable to races.**

Evidence: [record_eta](../supabase/migrations/002_workers.sql#L8) updates by tenant/job only; it stores no source GPS version. [jobs PATCH](../app/api/jobs/route.ts#L6) approves an ETA using only job ID, tenant and a boolean.

Failure scenarios: event A starts routing, event B arrives later and finishes first, then A overwrites B's ETA. Separately, a controller reviews ETA A, fresh GPS changes it to ETA B, and the unversioned approval approves B even though B was never reviewed. These are source-derived concurrency scenarios, not races reproduced against a live database in this audit.

Recommendation: store immutable ETA versions linked to source event, destination/route version, calculation time and provider. Update current ETA only if its version is still current. Approval must name the exact ETA version and record approver/time; reject a stale approval with 409.

Acceptance: reverse the completion order of two routing calls and retain the newest valid result. Change ETA between display and approval and require review of the replacement.

**F04 — P1: ETA freshness, failure state and publication are not modeled adequately.**

Evidence: [OsrmRouting](../lib/providers.ts#L5) returns `null` on failure. The tracking route retains any previous job ETA. Jobs have a timestamp and approval boolean but no validity, source time or routing-error state. [record_eta](../supabase/migrations/002_workers.sql#L8) clears approval on every successful recalculation. [whatsapp](../lib/domain.ts#L18) includes the existing ETA and last GPS timestamp without a stale warning; this formatting behavior was reproduced locally.

Impact: an old, already-approved ETA can remain visible after routing stops working, with no indication that the newest GPS was not incorporated. Conversely, frequent healthy GPS updates clear customer approval continuously. The integration dialog's claim that routing “fails closed” overstates the actual UI behavior.

Recommendation: represent ETA validity, calculation/source timestamps, provider status, freshness thresholds and publication rules explicitly. Mark a retained estimate stale; never imply that it is newly confirmed. Decide whether customer publication is manual per version, tolerance-based, or periodically reviewed. Add stale warnings to operational messages.

Acceptance: test healthy GPS with routing down, GPS itself stale, no route, recovery and frequent recalculation. The UI, customer portal and update text must agree on validity.

**F05 — P1: Job lifecycle and vehicle load status can contradict each other.**

Evidence: vehicles default to `Empty` in [the schema](../supabase/migrations/001_foundation.sql#L8). [jobs PATCH](../app/api/jobs/route.ts#L6) changes job status/controller only. The lifecycle trigger does not synchronize vehicle state. [whatsapp](../lib/domain.ts#L18) reads the vehicle's independent `load_status`.

Reproduction: advance an `At Loading` job to `Loaded` while its vehicle remains `Empty`; the MCY text says `Status: Empty`. The local probe confirms this, and source review confirms there is no synchronizing write in the dispatch path.

Recommendation: define the authoritative load model. For a single-load workflow, update lifecycle/load state atomically. For partial loads or multiple consignments, derive load state from active consignments and explicit loading/offloading events rather than a loose boolean.

Acceptance: create a new empty vehicle, complete loading and delivery through the real API, and assert the drawer, table and generated update show the same supported load state.

**F06 — P1: ETA routing does not model the active loading/delivery stop.**

Evidence: [jobInput](../lib/domain.ts#L21) and the jobs table have a single destination coordinate pair, with loading represented only by names/codes. [tracking/route.ts:6](../app/api/tracking/route.ts#L6) routes to that final destination even for `En Route to Loading` and `At Loading` jobs.

Impact: during collection, the estimate ignores the loading stop, its service duration and possibly the required route to collect cargo. The result is road-based travel time, not a complete operational delivery ETA.

Recommendation: add ordered stops with coordinates, stop type, windows, planned service time and actual arrival/departure. Determine the active stop from the lifecycle and distinguish ETA-to-next-stop from estimated final delivery.

Acceptance: a collection job routes to loading first; a loaded job routes to delivery. A multi-stop example includes service time and updates estimates as stops complete.

**F07 — P1: Database permissions do not preserve the claimed GPS authority boundary.**

Evidence: [vehicle_write](../supabase/migrations/001_foundation.sql#L37) is a controller `FOR ALL` policy over entire vehicle rows. No column-level restriction prevents an authenticated controller from directly changing latitude, longitude, GPS timestamp, provider or `simulated` through PostgREST. The schema comment says sensitive GPS writes are worker-only, but the policy does not enforce that.

Impact: a permitted controller can alter a “confirmed GPS” position without a tracking event. This is an integrity/provenance problem within an authorised tenant, not a demonstrated anonymous tenant-isolation escape. UI-only field restrictions do not repair it.

Recommendation: revoke broad telemetry-column writes. Provide narrowly scoped RPCs or column grants for fleet metadata, while worker-only functions own confirmed telemetry. Manual operational locations must be separate, explicitly labelled records. Make tenant ownership immutable outside a dedicated audited administrative process.

Acceptance: a controller may edit permitted fleet metadata but direct updates to confirmed GPS fields fail. A normal provider event still updates position and records provenance. Test a controller authorised for two tenants against attempted row transfers.

**F08 — P1: Exceptions have no recovery workflow.**

Evidence: [transition](../lib/domain.ts#L17) rejects normal progression from `Exception`; the database trigger also rejects it. The [dispatch UI](../components/control-tower.tsx#L48) disables progression and provides no resolution operation. The blocked domain transition was reproduced locally.

Impact: a controller can flag an exception but cannot resume the job through the application. An emergency database edit becomes the practical recovery mechanism. There is no structured reason, previous state, owner or resolution evidence.

Recommendation: implement exception records with type, severity, reason, owner, affected stage and allowed recovery actions. Resolve through an atomic, authorised operation that validates the selected recovery stage and records the reason. Keep cancellation distinct.

Acceptance: flag an in-transit job, record an owner/reason, resolve it, resume its valid stage and retain a complete history. Test repeated/conflicting resolution attempts.

**F09 — P1, pending the intended privacy matrix: document access is tenant-wide.**

Evidence: [document read policies](../supabase/migrations/001_foundation.sql#L29), [Storage download policy](../supabase/migrations/001_foundation.sql#L51) and [document GET](../app/api/documents/route.ts#L5) require membership, not document-specific authorisation, verification or release-to-customer status.

Impact: a `customer_viewer` can read all tenant document metadata and obtain access to all files in that tenant bucket path, including unverified material, driver licences and insurance. If that is explicitly the agreed role model, this is consistent with that narrow model. It does not implement the original requirement for document access permissions and authorised POD release.

Recommendation: approve a document/role privacy matrix, add customer-release and sensitivity rules, and enforce the same rules in Storage RLS. Protect direct bucket listing/download as well as the web endpoint. Treat verified PODs as versioned evidence so later edits cannot silently invalidate a closed job's basis.

Acceptance: a viewer can retrieve an authorised released POD and cannot retrieve an unreleased POD or restricted driver record through either API, Storage listing, known path or signed-URL creation.

**F10 — P1 release gate: green tests do not validate the live production workflows.**

Evidence: [browser tests](../tests/e2e/workflows.spec.ts#L2) run against the fictional demo without Supabase settings. Job creation/advance and message approval/history therefore mutate local React/storage state. The unauthenticated check accepts any status >=400 for two APIs, including misconfiguration errors. The pgTAP suite tests selected RLS cases and GPS ingestion but not memberships administration, Storage policies, approval races, complete SQL lifecycle/POD closure, load-state synchronization or ETA retry.

Impact: authentication, real uploads, authorised downloads, live dispatch and worker recovery could fail while all current checks remain green. Browser page errors are logged, not collected as a failing assertion.

Recommendation: add seeded Supabase-authenticated integration/browser fixtures with distinct users and roles. Exercise raw PostgREST and Storage alongside Next endpoints. Separate demo UI tests from production-path tests. Add route/provider fault tests and concurrency tests for F02–F09.

Acceptance: prove an authenticated create → dispatch → loading → delivery → verified POD → closure journey, with an isolated second tenant, denial assertions at every boundary, and actual private file bytes. Require stable expected error codes and fail on unexpected browser errors.

## Further production work

**F11 — P2: Assignment and document associations need stronger invariants.**

The schema allows several active jobs for one vehicle; the UI selects the first matching job from an unordered collection and the webhook routes all matches. Planned work may legitimately overlap, but a current-assignment model is absent. A document's job and vehicle each belong to the tenant, yet can refer to different vehicles within that tenant. The POD gate checks verified kind/job, not a durable proof/version binding. Add explicit active assignment, conflict handling, route/driver assignment history and association checks. Prove that concurrent dispatch cannot make one truck perform two mutually exclusive live jobs. Relevant sources: [jobs/documents schema](../supabase/migrations/001_foundation.sql#L9), [job selection](../components/control-tower.tsx#L27).

**F12 — P2: Audit logs cannot reconstruct operational changes.**

[audit_change](../supabase/migrations/001_foundation.sql#L17) stores generic strings such as `jobs update`, without before/after values, status transition, source event, changed columns, actor type, request ID or approval evidence. Triggers cover insert/update, not deletes; approvals have booleans without approver/time/hash columns. Add immutable structured domain events and snapshots of material changes, including denied/failed privileged operations in a separate security log. Record document versions, membership changes and the exact approved ETA/message version. Test reconstructing a dispatch dispute and a POD approval from stored evidence.

**F13 — P2: Alert monitoring lacks a workable incident lifecycle.**

[monitor_fleet](../supabase/migrations/002_workers.sql#L9) creates alerts but does not resolve them when conditions clear. Acknowledging an ongoing condition permits the same alert to be recreated next run. Deduplication by vehicle/title collapses multiple expiring documents; driver licence/PrDP dates in `drivers` are not checked. Missing PODs and update-due reminders are not monitored here. Add condition/resource keys, first/last seen, resolved/snoozed/acknowledged states, owner, escalation and recovery. Acceptance should cover an alert appearing, acknowledgement, no duplicate storm, condition recovery and later reoccurrence; independently track two documents for one truck.

**F14 — P2: Workspace reads silently truncate and lack deterministic order.**

[workspace GET](../app/api/workspace/route.ts#L3) reads up to 1,000 rows per table, sequentially, without ordering, pagination, totals or a truncation warning. Filtering, counts and reports then use that subset. UI `.find()` assumes a useful ordering for current jobs and latest messages. Introduce tenant-scoped paginated endpoints, explicit stable ordering, server-side aggregate counts and separately paginated history. Add tenant filter parameters backed by membership checks/RLS. Test >1,000 jobs/documents and verify totals and exports match the complete authorised dataset. Benchmark before promising fleet-capacity numbers.

**F15 — P2: API results and error semantics are too weak for reliable operations.**

Jobs/document/alert PATCH operations do not verify an affected row, so a valid UUID with no matching row can return success. [failure()](../lib/server.ts#L8) maps most infrastructure, persistence and limiter failures to 400; rate limiting is not 429 and transient worker failures are not distinguishable 5xx responses. Add typed errors, request IDs, row-existence/expected-version checks and appropriate 401/403/404/409/413/429/5xx responses. Check every Supabase result, including membership/workspace refresh errors. Ensure user-visible failures persist with a retry action instead of an indefinitely loading screen after a five-second toast disappears.

**F16 — P2: Upload security and cleanup are preliminary.**

[document POST](../app/api/documents/route.ts#L7) parses the full multipart body before limiting it when `Content-Length` is absent; checks only short magic-byte prefixes; uploads before inserting metadata; and has no quarantine, malware scan or orphan reconciliation. The bucket's size/MIME limits are useful but are not malware scanning. Add enforced ingress/body limits, per-tenant storage quotas, scan/quarantine/release states, hashes, failure cleanup and reconciliation. Do not allow the direct Storage path to bypass a required scan/release policy. Test malformed files, oversized/chunked requests and metadata failure after successful object upload.

**F17 — P2: WhatsApp scheduling and message approval are only partial.**

[update cards](../components/control-tower.tsx#L50) calculate a next time from the first matching update, with no due-task scheduler or notification. Any historic update keeps the status “Approved update” even after the interval expires. [approval POST](../app/api/updates/route.ts#L4) inserts a draft and approves it in two transactions. The database allows approved text to be changed by an authorised controller without automatically clearing approval. Add immutable message versions, transactional approval, approver/time/source identifiers, sorted latest-history queries, due tasks and explicit copied/opened/sent/acknowledged distinctions where measurable. Preserve the human send requirement; opening WhatsApp is not evidence of delivery.

**F18 — P2: Demo mode and identity UX need explicit production behavior.**

[page.tsx](../app/page.tsx#L5) automatically opens demo mode when either Supabase value is missing. This does not expose real records, but a misconfigured production hostname can display a convincing fictional operation instead of failing visibly. Add validated server configuration and an explicit demo opt-in. Login redirects include error query values that [the page](../app/login/page.tsx#L4) never displays. Password reset, MFA and invitation/activation flows are missing. Provide clear no-membership, expired-session, recovery and configuration-failure states; verify hosted Auth settings and rate limits rather than assuming the local config applies remotely.

**F19 — P2: Permissions and fleet scope are represented inaccurately in the UI.**

The workspace returns the most privileged role across all memberships, then uses it globally for controls; backend membership checks still protect each mutation. A user who controls A and only views B can nevertheless see controller controls for B. In combined scope, handover notes, AI summaries and team management default to the first tenant, which is not clearly communicated. The AI result's `source` is not displayed for production fallback summaries. Return a per-tenant capability map, require a named tenant for tenant-owned actions, clear summaries on scope changes and display rule-based/AI provenance. Test mixed memberships and a denied mutation without misleading success UI. Sources: [workspace role](../app/api/workspace/route.ts#L3), [handover/team](../components/control-tower.tsx#L53), [summary](../app/api/summary/route.ts#L5).

**F20 — P2: Management, reporting and handover features are incomplete.**

Fleet/driver creation and profiles exist, but editing, reassignment, archiving, bulk import and provider configuration lack UI workflows. Grouping is a free-text vehicle field, not a managed group entity or group-specific access boundary. Team access needs a pre-provisioned Auth UUID; it is not invitation/onboarding. Reports compare current ETAs to scheduled times; there are no durable actual loading/delivery times or historical SLA metrics. Handover is a note feed, not a shift with ownership, acknowledgement and outstanding-work transfer. Implement these in scoped increments after F01–F10 rather than describing the six product phases as complete.

**F21 — P2: Android readiness is conceptual rather than a delivered API contract.**

Domain types and Supabase storage can be reused, but web routes authenticate via cookies and mutations enforce browser-origin behavior. No versioned bearer-token API, mobile session tests, driver identity/permission mapping, OpenAPI contract, pagination contract or offline/idempotent command protocol exists. Define the mobile audience first—driver, customer or controller—and add narrow JWT-based endpoints/RPCs and conformance tests before starting an Android implementation.

**F22 — P2: Accessibility and interface failure states need dedicated verification.**

[modal markup](../components/control-tower.tsx#L57) declares dialog semantics without focus capture/trapping/restoration or inert background content. Map markers expose arrow text rather than an explicit vehicle accessible label. Mobile testing covers one viewport and one page, not document forms/dialogs or assistive technology. Page navigation is state-only, so routes cannot be deep-linked and browser history does not reflect feature navigation. Add accessible dialog primitives, labelled controls, persistent errors, empty states, URL-backed navigation and automated/manual accessibility checks. No WCAG conformance claim is supported by the present tests.

**F23 — P2: Production infrastructure is a runbook, not an operating system.**

No app host/preview, scheduler, provider credential registry, production ingress limits, backup configuration, tested restore, Storage-object backup, telemetry retention or monitoring integration is deployed. The webhook supports one configured tenant/provider pair per deployment and uses a reusable bearer credential rather than provider-native signatures/rotation. Application rate checks do not cover every endpoint or direct PostgREST/RPC writes; the rate table has no retention cleanup. Document actual RPO/RTO and service targets, provision staging first, configure monitoring/redaction/alerts, deploy durable workers, run a restore drill and collect provider acceptance evidence before release. [Deployment notes](DEPLOYMENT.md) correctly acknowledge much of this unfinished work.

**F24 — P3: Schema/domain alignment and data constraints need a pass.**

The TypeScript models declare driver, coordinate, GPS and ETA fields non-null where PostgreSQL permits nulls; they omit publication/provenance fields. Runtime responses are cast rather than parsed. SQL has fewer length/coordinate/business constraints than web Zod inputs, which are bypassable by authorised direct PostgREST users. Job references are truncated random UUIDs without a uniqueness constraint. Dates in document views use the browser's locale/timezone while the workspace claims SAST. Add generated database types, response schemas, consistent null/unknown handling, immutable tenant IDs, appropriate database constraints, stable unique references and explicit operational timezones. Verify direct database API writes as well as form submissions.

**F25 — P3: Maintainability and CI depth need improvement.**

The main controller file contains approximately 41.7 KB across 65 lines and combines almost all pages, mutation orchestration and demo behavior. CSS is similarly compressed. A local shadcn-style Button is present; reusable form, dialog, table and status primitives are limited. Format the source and extract feature modules with shared query/mutation and capability layers. Pin CI actions/tool versions deliberately, add scheduled full dependency auditing (current CI explicitly gates production dependencies), authenticated integration tests, provider fault tests, accessibility checks and load/restore exercises. Add PR branch protections after required checks are agreed; repository settings were not inspected by this audit.

**F26 — P3: Delivery documentation and remote state have drifted.**

Local documentation commit `e45693e` was not part of the remote PR head during this audit; the PR remained draft with its initial title/body. The successful implementation CI is real, but some delivery notes still describe checks as pending. Publish an explicit release-candidate scope, link tested code revisions and retain an honest feature/limitation matrix. This audit does not update remote metadata or publish its findings to GitHub.

## Recommended delivery sequence

**Milestone A — Establish a trustworthy authenticated pilot.**

Owners: backend/security and QA, with MCY operations approving the policy decisions.

1. Agree the tenant-role/document matrix, active-job rule, load model and ETA publication policy.
2. Add authenticated Supabase fixtures and raw PostgREST/Storage denial tests (F10).
3. Restrict authoritative telemetry writes and preserve immutable approvals/documents (F07/F09).
4. Fix live synchronization, load consistency, active-stop routing and exception recovery (F01/F05/F06/F08).
5. Add exact row/version checks and useful error/recovery UI (F15/F18/F19).

Exit: two tenants and mixed roles complete the real dispatch-to-POD journey; a second controller sees changes; unapproved/restricted records are inaccessible through every exposed data path; no misleading load/GPS/ETA state appears in the MCY message.

**Milestone B — Make telemetry dependable.**

Owners: backend/integrations and platform, with QA running fault scenarios.

Implement the transactional outbox, durable ETA workers, source-version fencing, versioned approval, validity/failure states and incident lifecycle (F02/F03/F04/F13). Add one provider's native signature/payload adapter and per-connection credential rotation before adding further providers.

Exit: crash/retry/out-of-order/routing-outage/concurrent-approval tests pass. Ingestion has a measured receipt target, ETA processing has a measured completion target, and failed work is recoverable without a fresh GPS event.

**Milestone C — Complete daily operating workflows.**

Owners: product/frontend/backend with controller acceptance sessions.

Deliver fleet editing/reassignment/archive, managed groups, invitation/onboarding, due-update reminders, versioned document release/scanning, proper audit history, ownership-based handovers, pagination and historical event-based reporting (F11/F12/F14/F16/F17/F20/F22/F24).

Exit: MCY operators can run a representative shift without SQL edits, silently missing records, ambiguous customer scope or unrecoverable job states.

**Milestone D — Production release gate.**

Owners: platform/security, with MCY approving operating targets.

Provision separate staging/production projects, host, scheduler, monitoring, backups and private-file recovery. Run provider acceptance, expected-capacity load tests, security review, accessibility review, session-revocation checks and a restore drill (F23/F25). Record actual results and approve the residual limitations.

Exit: deployment/rollback and data/file recovery are demonstrated; on-call ownership and response procedures exist; critical invariants have automated regression coverage. Start with a deliberately limited fleet pilot before broad customer rollout.

**Milestone E — Android.**

Begin Android work once the web application's authenticated API and operating invariants are stable. Define driver/customer/controller audiences and implement the corresponding versioned mobile contract (F21), rather than building a second client against unsettled semantics.

**Immediate next implementation recommendation:** Milestone A, beginning with production-path integration fixtures and database write boundaries. A visual redesign or a second tracking provider would add less value than proving one secure, correct dispatch-to-POD journey.
