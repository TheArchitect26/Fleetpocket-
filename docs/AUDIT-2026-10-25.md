# Fleet Pocket operational audit — 25 October 2026

## Assessment and scope

Fleet Pocket has a credible, tested foundation for controlled fictional-data evaluation. It is not yet ready for MCY to rely on its alerts, communication approvals or live-provider operation without the work below. The recommended next batch is **ETA display validity, exact-version message approval, overdue updates, incident reconciliation and explicit customer selection**, followed by supervised hosted UAT.

Reviewed baseline: local commit `8e8d222fa91b418ebe583c2f124241b35eab330d`, published application `021e1b37021b96bc5fb3a3064ac8eb082e0e4e5a`. This pass changes documentation and adds read-only audit evidence; the findings below remain open. Earlier audits are historical and are reassessed here rather than counted as independent new defects.

Scope includes product flows, controller/customer permissions, API routes, all twelve database migrations and policies, GPS/ETA work/publication, documents, reporting, Auth/session handling, test launchers, CI and operating documentation. No production project, live provider, external messaging service, restore environment or deployed scheduler was available. This is not an independent penetration test, accessibility certification or sustained load test.

### Evidence

- [CI run 40198841699](https://github.com/TheArchitect26/Fleetpocket-/actions/runs/40198841699) was rechecked: application, database and authenticated-workflow jobs all passed on the published baseline. Results: 26 unit tests, 3 setup checks, 110 database assertions, 5 demo workflows and 6 authenticated workflows, plus lint/types/build; zero vulnerabilities reported in that run.
- [Read-only probes](audit/operational-probes-2026-10-25.mjs) were executed locally; [recorded observations](audit/operational-results-2026-10-25.json) expose five current behaviors. Run from the repository root with Node.js supporting `stripTypeScriptTypes`: `node docs/audit/operational-probes-2026-10-25.mjs`.
- Probes execute extracted pure helpers and explicitly mirrored UI/sanitiser branches. They do not run a browser, database or spreadsheet, and their success means the undesirable behavior was reproduced, not that a product requirement passed.
- Other findings are source-supported or deployment/coverage gaps, identified below. No newly demonstrated cross-tenant database bypass was established in this review. Existing denial tests are evidence for their covered scenarios, not a blanket security claim.

P1 means resolve before a pilot relies on the affected behavior. P2 means required operating, security, usability or scale completion; a P2 can become a pilot blocker for the intended customer/volume. Release gates marked P1 are missing evidence/capability, not necessarily exploitable bugs.

## Highest-priority findings

### A01 — P1 — An expired ETA can still be described as within the delivery window

**Evidence:** [domain helper](../lib/domain.ts#L18), [fleet table](../components/control-tower.tsx#L43), [retained snapshot](../components/use-workspace.ts#L20). The helper returns `unknown` after expiry. The table instead derives `late = timing === 'delayed'` and chooses Within delivery window whenever a non-loading ETA exists and `late` is false. The timestamp is also displayed without a view-level validity check. Dispatch/drawer retain cached timestamps too.

**Scenario:** a delivery ETA expires during failed polling. Domain timing becomes unknown, while the fleet row continues to show the old arrival and a reassuring window label. The local probe reproduces the branch mismatch. Server publication withholding is an improvement but cannot invalidate an already-cached browser display by itself.

**Next:** one shared presentation contract for value, stop, source, expiry, mode and unavailable reason. **Accept:** browser clock advancement plus failed refresh removes the valid-arrival presentation in every view and keeps unknown separate from on-time.

### A02 — P1 — Approval can enable sharing of text that was not approved

**Evidence:** [saveUpdate](../components/control-tower.tsx#L37), [editable preview/share controls](../components/control-tower.tsx#L67), [update API](../app/api/updates/route.ts#L4), [write policies](../supabase/migrations/001_foundation.sql#L41).

**Scenario:** submit text A; edit to B while the request/refresh is pending; editing clears approval, but A's eventual completion unconditionally sets approval true. Copy/Share then reads current B. The local state-sequence probe reproduces this logic; an actual delayed-response browser test is still needed. Interval changes also do not invalidate approval. The API inserts then approves in two requests, stores no dedicated approver/time/hash, and controller-level direct updates can rewrite an approved row. Audit before/after data helps investigation but does not bind sharing to an immutable approved version.

**Next:** transactional versioned approval with exact text/interval/job/source snapshot, approver and timestamp; copy/share the approved snapshot, and invalidate pending responses after editing. **Accept:** delayed save/edit, double click, failure between insert/approval, changed interval and direct approved-row mutation regressions.

### A03 — P1 workflow gate — Scheduled updates never become operationally overdue

**Evidence:** [update desk](../components/control-tower.tsx#L54), [update schema/API](../app/api/updates/route.ts#L4). Any saved update yields Approved update; next scheduled time is calculated but never compared with the clock for the badge. There is no reminder worker or notification record. The local probe shows an update 90 minutes overdue still labelled approved.

**Impact:** a controller may read approved as current, while the original requirement to identify vehicles needing updates is not met reliably.

**Next:** separate approval from due/overdue state and build a deduplicated reminder queue with acknowledgement/escalation. Keep human approval before sharing. **Accept:** all preset/custom intervals, boundary clocks, missing first update, retry and no duplicate reminders. Do not add automatic sending without a separate messaging design.

### A04 — P1 — Alert acknowledgement and condition resolution are conflated

**Evidence:** [monitor rules](../supabase/migrations/002_workers.sql#L9), [open-alert uniqueness](../supabase/migrations/001_foundation.sql#L12), [acknowledgement API](../app/api/monitor/route.ts#L6), [incident UI](../components/control-tower.tsx#L55).

Rules insert alerts but do not resolve recovered conditions. Acknowledgement removes a row from the open deduplication key, so the next monitor can create another alert for the unchanged condition. Delivery-risk monitoring compares raw `jobs.eta` without the current-history validity checks; expired estimates can continue generating risk. Expiry alerts deduplicate by vehicle/title, so several documents on one truck can collapse into one alert. Driver licence/PrDP date columns are not monitored, and missing PODs have no equivalent durable alert lifecycle.

**Next:** incident condition keys, owner, acknowledgement, resolution, recurrence and history; evaluate valid ETA evidence and each expiring document/driver record. **Accept:** source recovery, reoccurrence, multiple documents, expired ETA, missing POD and repeated acknowledgement scenarios. These are source-derived cases, not newly executed SQL witnesses.

### A05 — P1 integration gate — The gateway is not a live multi-provider operation

**Evidence:** [tracking route](../app/api/tracking/route.ts#L6), [configuration](../.env.example), [routing provider](../lib/providers.ts#L4). One configured bearer secret binds one tenant/provider. There is no native Cartrack/Netstar/MiX signature/payload adapter, per-connection registry, credential rotation UI or connection-health history. The UI's tracking settings are informational labels.

**Next:** integrate one authorised provider first, with connection-level credentials, vehicle mapping, native fixtures and health/recovery evidence. **Accept:** real authorised payloads, duplicate/out-of-order/stale/future readings, mapping rejection, rotation and provider outage. Use a contracted/self-hosted routing service; the example public OSRM address is not a production capacity agreement.

### A06 — P1 at scale — Record caps affect completeness very early in an operating day

**Evidence:** [workspace snapshot](../supabase/migrations/012_coherent_workspace_and_creation.sql#L4), [export](../components/control-tower.tsx#L42), [audit triggers](../supabase/migrations/001_foundation.sql#L25), [full audit snapshots](../supabase/migrations/006_operational_integrity.sql#L10).

Each collection is limited to 1,000 rows globally across authorised companies; no pagination/search API retrieves excluded rows. Active jobs are prioritised, but the cap is still global. Audit contains telemetry as well as handovers. For twelve active vehicles at one fresh reading/minute, event insert + vehicle update + enqueue's job update can produce at least 36 audit entries/minute before routing writes: the latest 1,000 can cover less than 28 minutes. This is source-based arithmetic, not a measured load result. Counts/export/history can be incomplete even with a small fleet; a warning banner does not restore records.

**Next:** server pagination, complete scoped export and separate operational timeline/handovers from high-volume telemetry audit. **Accept:** over 1,000 rows across multiple tenants, old-but-open work, stable page ordering, full exports and handovers surviving telemetry volume.

## Operating and product completion

### A07 — P2 — Several dashboard labels claim more than their data establishes

[Active helper](../components/control-tower.tsx#L17) counts Created jobs as active trips labelled In motion; [vehicle counts](../components/control-tower.tsx#L49) count every returned vehicle; [workload](../components/control-tower.tsx#L57) always displays On shift without a shift/attendance source. The Created-job probe executes the actual helper. Customer performance is a forecast snapshot, not actual completed-delivery performance.

**Next/accept:** distinguish registered, dispatched, moving, forecast and actual delivery states; remove attendance claims without attendance data. Test planned, unavailable, idle and completed work. Historical SLA reporting needs actual stage timestamps and an agreed metric definition.

### A08 — P1 for combined operations — Sensitive actions silently choose the first customer

[Handover and Team & access](../components/control-tower.tsx#L58) use the first tenant in a combined workspace; AI summary follows the same implicit selection. This can record an authorised action against the wrong company and can show the wrong membership screen. API/RLS checks do not prevent the user choosing the wrong authorised company. Mixed-role workspaces also use aggregate role flags in some action visibility, leading to allowed-looking controls that later fail.

**Next/accept:** require explicit customer confirmation/selection for these actions, compute capability per target tenant, and test staff-in-A/viewer-in-B plus multiple customer-admin memberships. No silent first-tenant fallback.

### A09 — P2 — Secure storage exists; the document operating lifecycle is incomplete

[Upload API](../app/api/documents/route.ts#L7) is vehicle-centred and does not accept a driver ID. Driver licences/PrDP kinds exist, but there is no full driver-document relationship workflow. Magic-byte/size checks and private Storage are useful; scanning/quarantine, orphan cleanup after metadata failure, supersession/replacement and UI release revocation are absent. Kinds are hardcoded rather than customer-configurable. Direct Storage access does not inherit every web upload check.

**Next/accept:** driver and vehicle evidence workflows, safe replacements/revocations, scanner/quarantine and reconciliation. Exercise cross-job/driver mismatch, failed registration, scan failure and expiry reminders for both driver date records and stored files. Keep current verified-POD/release isolation regressions.

### A10 — P2 — Fleet/job assignment cannot be maintained through normal operations

[Fleet API](../app/api/fleet/route.ts#L5) provides creation only. There is no normal edit/deactivate/import/driver-reassignment UI. Job driver is captured at creation while allowed vehicle metadata updates can later change its driver; the drawer reads the vehicle's current driver. That can diverge from the job's recorded driver without a dedicated reassignment event. Driver deletion through allowed database access is not covered by the insert/update-only audit trigger.

**Next/accept:** explicit audited edit/reassignment/deactivation commands with live-job constraints; test job/vehicle driver consistency, duplicate registrations/fleet numbers and history. Do not rely on direct database edits as the daily operating workflow.

### A11 — P2 — Identity and session recovery need a complete user journey

[Login](../app/login/page.tsx#L4) redirects failures to a query flag but does not render a useful credential error. Account invitations, recovery, MFA enrollment and tenant onboarding are external/manual. [Workspace refresh](../components/use-workspace.ts#L20) retains the old in-memory snapshot on 401 as well as network failure; actions are still server-authorised, but an expired session can leave prior personal/operating information visible.

**Next/accept:** clear Auth failures, no-membership guidance, account recovery/invitations, and an explicit privacy policy for 401/revocation versus offline snapshots. Test expiry, role removal, sign-out and shared-workstation behavior. No new cross-tenant read is claimed here.

### A12 — P2 — Dispatch supports the core sequence, not all operating exceptions

[Dispatch commands](../supabase/migrations/010_physical_load_and_dispatch.sql#L43) implement a fixed sequence and exception/resume. Controller assignment is the acting user's ID, Accepted is controller-entered, and no driver app exists. Cargo recovery, alternate completion, configurable exception types, vehicle reassignment and route correction are not implemented.

**Next/accept:** agree business rules before adding commands; include audit/version/fleet-load/ETA invalidation for each. Preserve the historical-POD/newer-load and no-op regressions. No evidence in this review reopens those already-fixed cases.

### A13 — P2 — Queue health is useful but does not establish current recovery or capacity

[Health/retry functions](../supabase/migrations/011_eta_coalescing_publication.sql#L149) count all failed rows, including historical work that can remain after a newer success or job completion. Retrying a completed job is rejected. Worker failures use a broad routing-or-persistence category, and HTTP healthy means this invocation did not fail, not that backlog age or end-to-end freshness meets an SLO. Recent-source expiry, cooldown, latency and provider quotas can reduce throughput below the nominal 40 calculations/invocation.

**Next/accept:** current-vs-historical failure reconciliation, freshness/backlog SLOs and structured failure categories. Test two concurrent workers/controllers, expired leases during ingest, slow routing and sustained fair service across tenants. The existing twelve-vehicle scenario and sequential fairness SQL test are not a multi-worker capacity test; no unexecuted concurrency hypothesis is reported as a proven defect.

### A14 — P2 — CSV formula neutralisation misses leading whitespace/control characters

[CSV builder](../components/control-tower.tsx#L42) escapes quotes and replaces only a first-character `=`, `+`, `@` or `-`. A leading tab before `=` survives; the local sanitiser probe confirms this. The probe does not claim Excel execution. User-supplied route codes allow control characters, so the path is not limited to administrator-authored fields.

**Next/accept:** a reviewed export policy that treats leading controls/whitespace and preserves data, plus fixtures for spreadsheet applications MCY uses. Quoting alone is not a formula-neutralisation policy.

### A15 — P2 — Error, rate-limit and request-boundary handling remain inconsistent

[Server mapping](../lib/server.ts#L26) is better for jobs/doc verification, but members/fleet/uploads/handover still throw generic errors for ordinary rejection, which become 500. Alert acknowledgement can return success for zero matched rows. Web API rate limits do not cover every direct authenticated RPC/Storage path; login/provider/edge limits depend on unverified external configuration. Upload uses Content-Length as an early check but parses multipart before its file-size check; the tracking route has the stronger bounded reader.

**Next/accept:** consistent status/request IDs, affected-row assertions, ingress body/time limits and documented limits for Auth/web/worker/direct-data paths. Test 403/404/409/413/422/429, oversized streamed multipart and failed dependencies. This is a boundary-completion finding, not a proven denial-of-service attack in this session.

### A16 — P2 — AI assistance currently covers aggregate summaries only

[Summary route](../app/api/summary/route.ts#L5) sends counts of open/critical alerts. It cannot interpret individual telemetry sequences, explain actual exceptions or detect anomalies from data it never receives. Server-side keys and a labelled deterministic fallback are sound boundaries.

**Next/accept:** define evidence-backed event context and human review before adding AI event analysis; test factuality, unavailable provider and handling of customer-authored text. Do not market the current count summary as predictive fleet monitoring.

### A17 — P2 — Test depth and accessibility remain behind operating complexity

Current tests cover valuable real Auth/RLS, POD, queue/publication and browser flows. They do not cover A01/A02's browser races, broad mixed-role access, populated-database scaling, sustained/concurrent workers, native providers, restores or independent penetration testing. [Dialogs/drawers](../components/control-tower.tsx#L61) lack a complete focus-management contract; keyboard shortcuts are not proof of accessibility. Map markers distinguish simulation but do not expose stale age in their accessible label.

**Next/accept:** add targeted regressions before fixes, then keyboard/focus/screen-reader/manual mobile acceptance and failure/load suites. Keep a coverage matrix mapping each claimed capability to evidence; test totals alone are insufficient.

### A18 — P1 release gate — Hosted operating readiness has not been demonstrated

[Deployment guide](DEPLOYMENT.md) describes intended schedules, backups and monitoring. Current environment observations show no provisioned live secrets/services. No actual test URL, worker/monitor execution history, file backup restore, rollback rehearsal, log/alert destination, retention process or provider contract was verified.

**Next/accept:** named owners and a dedicated hosted fictional-data UAT environment first; then schedule/failure alerts, database and Storage restore evidence, rotation/rollback and real-provider acceptance before a live pilot. Keep development testing separate from production approval.

## What has improved and remains supported by evidence

Historical paperwork no longer empties a newer load in the covered scenario. Same-state dispatch is a genuine no-op. Workspace reads use one statement snapshot. Job creation has an idempotency key, and committed writes survive display-refresh failure. Map viewport persists. Loading forecasts are excluded from delivery-timing metrics. GPS work is durable/coalesced and customer publication retains a separately reviewed source/version. Private-file ownership, customer release and tenant denial have real integration coverage. The local test launcher is exercised by CI.

Those improvements address important parts of the 24 October audit. Open issues here include R08/R10–R16's unfinished areas, more detailed communication/expiry cases, and remaining operating evidence; prior findings are not all reset to open.
